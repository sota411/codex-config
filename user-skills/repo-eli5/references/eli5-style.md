# ELI5の説明は、名前より先に仕組みを渡す

この規約は、公開されているMITライセンスの
[`Kyaa-A/eli5`](https://github.com/Kyaa-A/eli5/blob/main/skills/eli5/SKILL.md)
を、日本語のリポジトリ教材へ合わせて翻案したものです。説明を短くすることより、初見の読者が一度で仕組みをつかめることを優先します。ただし、単純化のために実装と異なる説明を作ってはいけません。

## 一つの章では、一つの核心だけを教える

repository modeでは、読者が最初に知るべき仕組みを三つ選びます。一つの章に複数の主張を詰めず、見出しだけでその章の結論が分かるようにします。

各章の本文は、図より前に五文以内で書きます。

1. 何があるのかを、読者が普段使う言葉で説明する。
2. それが何のためにあるのかを述べる。
3. 抽象的な仕組みなら、理解を助ける日常の比喩を一つだけ使う。
4. 専門用語が必要なら、仕組みを説明した後で「コードでは、これを〜と呼びます」と名前を渡す。
5. 例外や実装上の細部は、図の後にある「コード上の根拠」へ分ける。

前置きや「これから説明します」は書きません。最初の一文から答えを渡します。比喩は、元の仕組みとの対応を一文で説明できる場合だけ使い、飾りの物語へ広げません。

## 図は、直前の一文を見える形にする

図の前には、必ず「この仕組みがあります」という説明を置きます。図だけを先に見せたり、「まず全体像を見ます」のように内容を伏せたりしません。

主ラベルには、クラス名、ファイル名、内部識別子、説明していない略語を置きません。「音声受信・PCM変換」ではなく「Discordの声を、文字にしやすい形へ変える」のように、入力と結果が分かる言葉を使います。製品名や技術名が必要なら、小さい補助ラベルか根拠欄へ置きます。

図の直後には、どこから読み、何が分かるかを一文で書きます。図が省略した例外や別経路は`figcaption`で明示します。

## 根拠は、簡単な説明を邪魔しない場所へ置く

各章の末尾に`details[data-evidence-group]`を置き、その章を支える確認済みの事実と`file:line`を示します。推論や未検証事項は事実と分けます。読者は最初に簡単な説明だけを読み、必要になった時点でコード上の名前と根拠を開けます。

## クイズは、思い出す負担より理解の確認を優先する

自由記述は使いません。各問は四つの肯定文から一つを選ぶ形式にし、架空のcomponentやbehaviorを誤答へ混ぜません。回答後は正誤と理由をその場に表示し、正解かどうかにかかわらず次へ進めます。正解するまで選び直させたり、自動で次へ送ったりしません。
