# Blender の制作・保存・描画を確かめる

扱う工程の節だけを読む。実行版の API と手元のファイルを優先し、ここに挙げる過去版との差分を互換性の網羅表として扱わない。

## CLI では読み込みと実行の順序を守る

新規シーンをスクリプトから作る例:

```sh
blender --background --factory-startup --python-exit-code 1 --python make_scene.py
```

既存ファイルを編集する例:

```sh
blender --background input.blend --python-exit-code 1 --python edit_scene.py
```

`make_scene.py` と `edit_scene.py` は、その依頼のために作成したスクリプトを指す。シェルへ渡すパスは引用し、保存先を明示する。

CLI の引数は順に実行される。ファイルを読み込んでから設定を変更し、最後に描画する。読み込み前の設定は `.blend` の設定で上書きされ得る。`--python-exit-code 1` は CLI から実行した Python の例外を終了コードに反映するが、`CANCELLED` や出力漏れまで検出するものではない。保存・描画の完了と、今回生成したファイルを別に確認する。[公式 CLI と API](sources.md#python-cli)

MCP を使う場合も、接続先の Blender の版と実際のシーンを確認する。タイムアウト後の再実行では、処理済みかどうかを読み取ってから進める。接続を失った既存シーンを、新しい CLI プロセスで開いた別シーンへの操作で代用しない。

## 明示した対象を編集し、版による API の差を確認する

Data API は Object や Material を直接扱える。`bpy.ops` は選択、Active Object、Mode、Editor などに依存し、通常は生成物ではなく実行状態を返す。必要な Operator の Context を用意し、返値と対象データを確認する。

既存作品は対象の名前だけでなく所属や役割も確認し、指定範囲を編集する。複数のオブジェクトが同じ Mesh、Material、Node Group を共有している場合、一方への変更が他方へ及ぶ。個別変更なら必要なデータだけをコピーする。

過去のコードで特に確認する箇所:

| 箇所 | 既知の変更と対応 |
| --- | --- |
| Geometry Nodes の公開入力 | 4.0 で `NodeTree.interface` へ移行。実際の入力と識別子を調べる |
| Geometry Nodes Modifier の入力値 | 5.2 で RNA に移行。`getattr(modifier.properties.inputs, identifier).value` で設定し、読戻しと再評価で確かめる |
| Principled BSDF | 4.0 で複数の入力名が変更。実行版のソケットを確認する |
| Action の F-Curve | 5.0 で旧 `action.fcurves` 等が削除。対象 Object の Action Slot と対応する Channelbag を確認する |

単純なキーフレーム挿入で済む場合まで、低水準の Action 構築を自前実装しない。フレーム移動後の状態を測るには `scene.frame_set(frame)` を使う。[公式 API とリリースノート](sources.md#python-cli)

## 形状を決めてから材質と照明を詰める

まず配置、比率、シルエットを軽いプレビューで見る。立体として使うモデルは必要な複数方向から確認し、単一カメラ専用の作品はその用途に合わせる。見た目に影響しない裏側の作り込みを一律に要求しない。

材質では、色、粗さ、金属感、透過、テクスチャの尺度を分けて調整する。Normal や Displacement などのデータ画像は Non-Color として扱う。既存の色管理設定を引き継ぎ、新規作品では納品先に合う設定を決めて比較中は固定する。[公式の色空間](sources.md#rendering)

Material Preview は独自の HDRI を使う場合があり、Scene Lights / Scene World の設定によって最終照明と異なる。完成画像の確認には、意図した Render Engine、カメラ、照明、World、Compositor を使った出力を開く。露出や被写界深度で形状の不備を隠さず、原因となる対象を修正する。[Viewport の仕様と視覚的な反復](sources.md#rendering)

## 動画は代表フレームと短いプレビューから始める

FPS とフレーム範囲を決め、開始・中間・終了に加えて、接触や方向転換など変化の大きい箇所を確認する。可動部はピボット、Parent、Constraint、補間が意図した動きになっているかを見る。静止画だけでは動きの確認にならないので、軽いプレビュー動画または連続フレームを再生して確かめる。

重い最終描画の前に、代表フレームの実測時間から所要時間の目安を出す。形状や照明が変化する区間では負荷も変わるため、単純な掛け算は概算と明記する。

長時間の描画や後処理がある場合は、PNG や用途に合う EXR の連番を出力してから動画へ変換する。途中で止まっても描画済みフレームが残る。再開時は同じシーン・設定の有効な画像かを確認してから既存フレームを省略する。変更前の画像や破損ファイルを残したまま、上書き無効で再開しない。[公式の動画制作手順](sources.md#rendering)

## 保存したファイルと書き出したファイルを開き直す

出力先を分け、元の作品と変更後の作品を取り違えないようにする。別プロセスで保存した `.blend` を再読み込みし、変更したデータと必要な外部依存を確認する。配布時は画像・リンクライブラリ・キャッシュなどの依存を確認し、用途に応じて同梱、パック、相対パスを選ぶ。Pack ですべての種類の外部依存が解決すると仮定しない。

GLB 等の書き出しは依頼された場合に行う。納品用コピーで必要な変換を行い、編集用の構成を残す。書き出したファイルを空のシーンや利用先で開き、対象、寸法、向き、材質、必要な動きを確認する。Blender 固有のノードや機能が他形式へそのまま移るとは仮定しない。[再利用仕様と公開ワークフロー](sources.md#reuse)

完了報告では、Blender の版、生成物の場所、変更できる入力、保存後の確認、描画の確認範囲を記載する。動画なら解像度、FPS、尺も添える。表示できたことと、利用先のゲームや Web で動作確認したことは区別する。
