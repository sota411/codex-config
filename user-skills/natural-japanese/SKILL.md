# natural-japanese

事実、書き手の意図、指定された構成や書式を保ち、正しく読みやすい日本語にする。docsや記事には自動適用する。確認の深さは内容と残る懸念に合わせ、レビュー人数で品質を定義しない。

## モード

既存の呼び出し方を保つ。引数なし、または `[quick|full] <対象>` は執筆・推敲として扱う。

| 呼び出し | 目的と確認 |
|---|---|
| `write [quick|full] <対象>` | 素材から執筆する。既存文章がある場合は、依頼された箇所を推敲する。 |
| `quick`（既定） | lintと通読で日本語・事実保持・用途への適合を確認する。 |
| `full` | 全文の構成・読みやすさ・用途の必須要素を詳しく確認する。構成にはoutline、専門用語にはtermsを使う。 |
| `score [quick|full|exp] <対象>` | [診断手順](references/diagnose.md)を読み、文章を書き換えずスコアと理由を返す。 |
| `exp`（診断のみ） | 意味的検出も使う明示指定。初回ダウンロード等は診断手順に従う。 |

「ちゃんと」「しっかり」、対外文書、文字数だけを理由にフル工程や複数人レビューを義務化しない。品質を求める依頼には必要な観点を深く確認して応える。ユーザーがモード、人数、レビュー方法を指定した場合は、その指定を優先する。

## 執筆・推敲と確認

1. 読者、目的、素材、指定書式を依頼と資料から把握し、内容を左右する不足だけを確認する。数値、固有名詞、引用、事実と推測の区別を維持する。素材不足は言い換えで埋めない。
2. 主メッセージと構成を決める。新規執筆や構成を変える大幅改稿では[声のある下書き](references/voice-first-draft.md)を読む。局所修正・診断では不要。
3. 助詞、主語と述語の対応、係り受け、語順、読点、文体の統一を確認する。結論と根拠をつなぎ、専門用語を読者に合わせて説明する。自然な濃淡と既に良い表現を保ち、同じ修正を全文へ機械的に当てない。判断に迷う文だけ[読みやすさの原則](references/readability-principles.md)や[悪文パターン](references/readability-antipatterns.md)の該当項目で確かめる。
4. 下記のlintを1回実行し、全文を通読する。指摘は修正候補として文脈で判断し、採用・見送りと理由を把握する。lintの終了コード0や指摘件数だけでは、日本語の正しさや完成を判定しない。
5. 確認できた問題を修正し、変更した箇所と直接影響する流れを再確認する。新しい問題や未解決の懸念がなければ確認を繰り返さない。修正後も事実・意味・指定要件を満たすことを確認して仕上げる。

スクリプトは、このSKILL.mdのディレクトリを基準に絶対パスで呼ぶ。対象文書の場所へ移動してから相対パスで探さない。

```bash
uv run <skill-dir>/scripts/lint.py --json <文書>
```

ジャンルが分かれば `--genre essay|tech|business` を指定する。読解負荷は `--reading-load`、修正前後の指摘比較は `--baseline <前回のJSON>` を必要な場合だけ使う。実行できなかった場合はエラーを明示し、[手動チェック](references/manual-checklist.md)で確認する。手動確認をlintの実行成功とは報告しない。

## 追加レビューと詳細資料

- 構成、読みやすさ、文書形式の懸念が残る場合、または追加レビューの明示依頼がある場合に、必要な観点だけを独立レビューへ渡す。人数は固定せず、執筆と指摘の採否・統合はメインが担う。委譲できない環境ではメインが同じ観点を確認し、独立レビューは未実施と伝える。
- 構成の確認には `scripts/outline.py`、専門用語の初出確認には `scripts/terms.py` を使う。詳細な判断方法、素材収集、改稿、終了条件は[推敲ガイド](references/revision-guide.md)の必要な節だけを読む。
- 文体の判断に迷った場合は[文体原則](references/writing-constitution.md)、該当する検出カテゴリは[禁止表現](references/forbidden-patterns.md)・[翻訳調](references/translationese.md)、ジャンル差は[ジャンル別指針](references/genre-notes.md)を読む。全資料を一括で読まない。
- 文書形式に必要な要素を確認するときだけ、[議事録](references/doctypes/minutes.md)、[レポート](references/doctypes/report.md)、[ガイド](references/doctypes/guide.md)、[メモ・企画](references/doctypes/memo.md)、[スライド](references/doctypes/slide.md)から該当する1つを読む。ユーザーの指定構成を優先する。
- 指定場所またはプロジェクトに既存の `style-profile.md` があれば尊重する。プロファイルの新規作成は、ユーザーが求めた場合だけ[テンプレート](assets/style-profile-template.md)を使う。個別の表現への指摘を普遍的な禁止規則へ拡大しない。
- 中間ファイルは一時領域へ置く。後片付けは自分が作った一時ファイルに限り、ユーザーの原稿、既存バックアップ、求められた成果物は保持する。
